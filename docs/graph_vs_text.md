# Результат 2. Підграф у контексті: «лише текст» vs «текст + підграф»

_Згенеровано `python src/eval_rag.py graph-ab` 2026-11-23; питання — `eval/graph_questions.jsonl` (12 шт.), роль analyst, детермінована генерація._

## Метод

1. **Entity linking** (`src/graph_context.py::GraphContext.link`): запит → uid вузлів за `uid`, `code` і назвою вулиці з `name_uk` (з відмінками), максимум 4 сутності.
2. **Підграф** (`subgraph`): режим «окіл» (1–2 кроки в обидва боки) або «ланцюг впливу» (за напрямом ребер, до 5 кроків; обирається за словами «вплине/залежить/зачепить…»); ліміт — 25 ребер; лише фіксовані READ-шаблони Cypher.
3. **Лінеаризація** у промпт: `[g1] INC_317 (TrafficAccident) -CAUSES-> CONG_881 (TrafficCongestion)`; модель цитує факти як `[gN]`, цитати перевіряються (`rag.check_citations`).
4. Для кожного питання два прогони з однаковими параметрами: `use_graph=false` і `use_graph=true`.

## Висновок (числа)

- Entity linking дав непорожній підграф у **11 з 12** питань (92%); для решти режим «граф» еквівалентний «лише тексту» — перевірте ID у ваших питаннях командою `python src/graph_context.py "<питання>"`.
- Токени на вхід: у середньому **2089 → 2300** (Δ = +211, +10%); на вихід 213 → 267.
- Затримка: 14.9 с → 16.6 с (Δ = +1.6 с).
- Правильність (середнє з 2) за 12 оціненими: текст **0.17** → граф **1.08**; пояснюваність: **0.00** → **0.83**.

> Обмеження: підграф береться з графа ЛР 9 без фільтра за sensitivity, тому для production його треба фільтрувати за роллю так само, як текстові фрагменти.
